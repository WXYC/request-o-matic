Request-line bans: how it works

How WXYC blocks an abusive listener from the request line — what actually gets banned, where that state lives, who is allowed to issue one, and why there is no ban button on the request posts in Slack.

The short version

  • A ban targets a device, not a person and not an account. The target is a UUID the iOS app generates and stores in the iCloud Keychain.
  • Ban state lives in Backend-Service. Request-O-Matic is a thin proxy over it, so there is one table and one audit trail no matter which surface issues the ban.
  • A banned listener is shadow-banned: their app behaves normally, and nothing reaches Slack, the parser, or the library search.
  • Only a few accounts can ban. The authorized set is a short break-glass list from configuration, unioned with a roster that moderators edit from Slack.
  • There is no ban control on public request posts. That is deliberate and explained below — it is not a permissions hole, and it is not an oversight.

What gets banned

Every request from the iOS app carries an X-Device-Fingerprint header: a UUID the app generates once and keeps in the iCloud Keychain, separate from the login session. That UUID is the ban target.

Choosing the device rather than the account is what makes the ban meaningful at all — request-line listeners are anonymous, so there is no account to ban. Storing it in the iCloud Keychain is what makes it durable: it survives signing out, signing back in, and reinstalling the app on the same Apple ID.

Known limit

A determined person can disable iCloud Keychain, reinstall, and arrive with a fresh fingerprint. This is accepted. The system is built to deter a persistent nuisance, not to defeat someone committed to evading it.

Three kinds of request carry no fingerprint at all and therefore cannot be banned by any surface: an unauthenticated caller, an iOS client older than 3.2, and a post that degraded before the header was read. There is nothing to act on, so no ban affordance is offered for them anywhere.

The fingerprint is never displayed

A stable per-device identifier shown in a channel that DJs read all shift is a de-anonymisation vector — it lets anyone correlate a listener's requests across weeks. So the fingerprint travels as private Slack message metadata, invisible in the rendered post, and is read back only by the code that acts on it. It is never rendered as visible text, and this document does not print one either.

How a request flows, and where the ban check sits

From the listener's side, a ban is invisible. The app receives a refusal it already swallows, so there is no error message, no "you have been banned" screen, and no signal that would tell someone to go get a fresh fingerprint. That is the point of a shadow ban.

Who can ban

The authorized set is the union of two lists:

ListLives inEdited byPurpose
Break-glass allowlist A Request-O-Matic environment variable Anyone with deploy access, by hand A short administrator list that keeps working when everything else is down
Moderator roster Backend-Service Moderators, via a slash command in Slack The list that is actually maintained day to day

Authorization is checked twice on every ban — once when the menu item is chosen, and again when the reason modal is submitted. The second check is not redundant: it means a hand-crafted submission cannot skip the first one.

Fails closed, in the useful direction

If Backend-Service is unreachable, the roster half is simply missing and the authorized set shrinks to the break-glass list. It never widens. An outage in the roster service must not turn into ban rights for the whole workspace — and the thing you are left holding is the administrator list, which is the correct thing to be left holding.

The refusal a moderator sees in that situation says "we could not check", not "you are not authorized". Those are different facts, and telling someone the second when the truth is the first sends them to argue about their permissions during an outage that has nothing to do with them.

Why there is no ban button on request posts

There used to be one: an overflow ("…") menu under every request post in the channel, holding a single "Ban requester" item. It is gone, and the reason is worth stating precisely, because the obvious reading of it is wrong.

It was never a permissions hole. Every DJ could see the menu; only the authorized handful could use it. An unauthorized click got a private refusal that nobody else in the channel saw, and no ban was issued.

But that is still the wrong design, for a reason that has nothing to do with security. A visible control reads as an available one. DJs seeing a "ban requester" option under every listener message reasonably concluded the station was handing ban rights to everyone — and a moderation control sitting in a channel people read all shift invites questions that its presence cannot answer.

The constraint that forces this

Slack has no per-viewer block visibility. A channel message is one payload delivered identically to every member. There is no field that says "show this element only to these users", so the menu could not be conditioned on who was looking. Matching visibility to authorization is only reachable by changing where the menu is posted — not by changing how it is built.

So the affordance was detached from the public post, and is being re-homed to a moderators-only channel, where channel membership does the hiding that Block Kit cannot. What that leaves in place today:

  • The public request post still carries the fingerprint in private metadata. Removing the visible control deliberately did not remove the ban target.
  • The whole click-to-ban path is still deployed and tested — signature verification, the double authorization check, the reason modal, the ban call, the confirmation, the footer edit. None of it is being rebuilt.
  • The handler is channel-agnostic. It reads the channel out of the click it receives and never checks it against the request channel, so the same menu works unchanged wherever it is eventually posted.

Until then, bans are issued through the HTTP admin API, which is how every ban has been issued to date.

Issuing a ban today

  1. Find the fingerprint. Query the Request-O-Matic analytics project for per-device request counts. The exact query is in docs/admin-bans.md. Note it is that project specifically — running it against the iOS app's project returns zero rows, which looks identical to "the fingerprint was never recorded".
  2. Issue the ban against the admin API with a reason. Reasons are not decoration; they are the only record of why, and the person reading it later will not be you.
  3. Verify by listing current bans. The listener is not told anything, so the ban table is the only confirmation that exists.
  4. Unban by deleting the entry. Bans are cheap to reverse and there is no penalty for reversing one.

Full endpoints, arguments, status codes, and worked curl examples live in docs/admin-bans.md. They are deliberately not duplicated here — one copy of a command is maintainable, two copies drift.

What this system does not do

  • It does not record who issued a ban, in Backend-Service. The acting Slack user is captured in Request-O-Matic's own logs, but the stored ban's actor column expects a WXYC account and a Slack user has no row there. "Who banned whom" therefore survives only in rotating service logs.
  • It does not keep a banned listener's messages. A ban is currently a hard drop, so once someone is banned the station stops being able to see what they are sending — including an escalation from nuisance to something the station would have a duty to act on. Quarantining that traffic to a moderators channel is planned, not built.
  • It does not derive moderators from station roles. Ideally being a music director or station manager would simply imply ban rights, with no list to maintain. That needs a mapping between Slack accounts and WXYC accounts that nothing stores today.
  • It has never been used in anger. No ban has ever been issued against a real listener. This is insurance, and it is worth remembering that when weighing how much machinery it deserves.
